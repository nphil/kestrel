# Kestrel Scrypted plugin

Kestrel watches selected Scrypted cameras for wildlife visits, stores visits and review corrections in SQLite, links a clip to every camera visit (the Events Recorder's, or one cut from the NVR's continuous recording) and keeps its own copy of it, learns from corrections with CLIP, and ingests BirdNET-Go detections over MQTT. Home Assistant reads the authenticated JSON and media API; this plugin does not publish MQTT discovery or Home Assistant events.

The first run creates a private API key shown read-only in the plugin settings. Add the base URL `http://192.168.1.69:11080/endpoint/@nphil/kestrel/public/` and that key to the Home Assistant Kestrel integration. Every JSON and media request uses the `X-Kestrel-Key` header.

Choose the wildlife cameras in Settings. The initial set is Backyard (88), Back Door (103), Front Door (104) and Bird (106). BirdNET-Go subscribes to the configured MQTT topic (default `birdnet`) and its subtopics; the MQTT username and password are copied from Scrypted MQTT device 202 when those settings are empty.

Visits are created from Scrypted animal detections after a 30-second unidentified grace period, with a 10-minute per-camera/species cooldown. The cooldown counts earlier *seen* visits only: a bird that was merely heard (BirdNET-Go) never blocks a sighting of it, and the sighting is linked to the call when the call was heard within two minutes of it on the same camera. Snapshot and crop media are retained for 30 days unless a species best photo or correction uses them; visit rows are kept for three years. Nightly maintenance runs at 03:30 and keeps the plugin's media under a 300 MB budget.

Detections of one animal at one moment are one visit, whatever each detection is labelled: a detection on the same camera within 5 seconds of a visit's start (or of the last animal detection folded into it, for up to one cooldown) joins that visit instead of starting another. The higher-scoring label keeps the species (a tie goes to the earlier detection) and supplies the photo, the other label is kept as a `model` suggestion, and only one `visit_new` is published; later merges publish `visit_updated`. Visits a person has corrected or confirmed are never changed by a merge. A recorded clip that starts up to 5 seconds after the visit's start still counts as that visit's clip (Events Recorder begins recording a moment after the detection).

**Camera visits carry the classifier's confidence (`labelScore`).** Scrypted's NVR puts a label on an animal only when the wildlife classifier is at least 70% sure and never passes its confidence on (the SDK's `labelScore` is set for face recognition only, and the NVR strips it unless debug mode is on), so `score` on a seen visit is the camera's box score. When a detection is committed Kestrel asks the Wildlife Classifier (device 248) about the saved crop and stores the confidence in the label it gave as `labelScore` (null when it cannot say; Scrypted's own `labelScore` is used if an event ever carries one). Two detections of one animal are ranked by `labelScore` when both have one and by box score otherwise (never a mix), and the panel shows `labelScore` instead of the box score.

**Heard visits say how sure Kestrel is.** BirdNET-Go runs BirdNET v3.0 and Perch v2 on the same microphones (Back Door and Backyard; v3.0 is gated at 0.50). v3.0 makes the call, Perch is a second opinion, and scores are never merged (`audio-eval/results.md`). BirdNET-Go sends ONE message when both models name the same bird (the higher score wins; `Model` says whose) and two when they differ, so each message is kept as a row of `heard_calls` (model, species, score, `occurrence`, clip, the visit it belongs to; pruned after 30 days) and waits 6 s (9 s for the second opinion) before it becomes a visit, so a disagreement is known before anything is announced. Messages that name the same bird within the cooldown are more evidence for the visit they already have, never a new visit. The main model is the best one heard in the last 24 hours, so retiring either model needs no change here. Each new heard visit carries a `tier` (`likely`, `possible` or `check`), why (`tierWhy`), `occurrence` (BirdNET-Go's chance of the species here this week), `commonness` (how common local sightings say it is at this time of year, `seasonal.ts`), `repeats` (calls of the same species on the same microphone within 5 minutes of the first) and `models` (what each model said: the call that `named` the visit, models that `agree`, a model that named an `other` bird):

- **Check** (review queue): the models name different birds and one is at least 50% sure (the visit is named by v3.0, Perch's bird is stored and offered as a `model` suggestion), or only the second opinion heard it, or a weak call of a bird never recorded or rare here.
- **Likely**: a clear call (80%+), or a good one (60%+) heard again, of a bird that is not rare here (a rare bird has to be heard three times). Only a Likely call may be announced as a first-ever species (`notify`) or counts toward the species list, the camera's latest sighting and "first ever".
- **Possible**: everything else. It is stored and listed but kept quietly: it does not count, is never announced, and does not link to or doubt a camera sighting.

Evidence only adds up (a repeat can promote a visit in place and publishes `visit_updated`, a quiet minute never demotes one), a visit a person has confirmed or corrected is never re-rated, and visits from before this layer have no tier and count as they always did. `usual` suggestions come only from visits a person confirmed or corrected (last 90 days).

Corrections can be undone. Undo removes the matching learning example and recomputes the best photo for each affected species.

`GET events?after=<seq>&timeout=<seconds>` is a long poll: `timeout` is in seconds, clamped to 0-25 (missing or unparseable means 25), and the request returns as soon as an event is available. At most 100 requests can wait at once. Events are `visit_new`, `visit_updated`, `visit_deleted` and `camera`:

- `visit_deleted` (`{ "id": "<visit id>" }`) is sent for every visit row that is removed, so open dashboards can drop it: the split-visit repair, the duplicate and insect clean-ups, and the three-year retention prune. The row is already gone when the event is published.
- `camera` carries the same list as `GET cameras`. Cameras are re-checked every 30 seconds, but the event is published only when the list differs from the one last published: at start-up, and then when a camera goes offline or comes back, its health or dropped-connection count changes, its name or wildlife flag changes, or its latest visit changes (a new visit, a merge that changes its species, a removed visit). An idle plugin publishes nothing.

`GET media/camera/<cameraId>.jpg` is the camera's latest visit snapshot (404 if it has none); the Home Assistant "latest animal" images, and so the phone notifications, use it. `GET media/live/<cameraId>.jpg` is a current picture from the camera, for the Live tiles of cameras that have no NVR card; every camera in `GET cameras` carries its path as `picture`. It is taken with Scrypted's `takePicture` only when someone asks for it (a periodic request, at most 960 px wide, JPEG quality 75), kept in memory only, shared by requests that arrive together and reused for 15 seconds, so a camera is asked for a new picture at most once per 15 seconds; a camera that cannot answer is left alone for 15, then 30, then 60 seconds, and a capture that never answers is given up on after 23 seconds. The response is `Cache-Control: no-store` with an `ETag` and a `Last-Modified` (a matching `If-None-Match` gets a 304). If the camera cannot give a picture, its latest visit snapshot is sent instead, and 404 only if there is neither. Ids that are not cameras are never captured.

**Clips.** Every seen visit starts with `clip.state: "pending"`, and its clip is looked for in this order, every 5 seconds: (1) the **Events Recorder**'s clip (its `getVideoClips`, or `/NVR/clips/<camera>/videoclips`); (2) once the visit is overdue (90 seconds after it started, longer than the Events Recorder's own 60 s clip plus 10 s after the event, so a clip it is still writing is never pre-empted) a clip **cut from the NVR's continuous recording** (the camera's `VideoRecorder`, `getRecordingStream`): from 5 s before the visit started to 10 s after its last detection (the plugin knows the last detection while the visit is current; otherwise the visit is assumed to have lasted 20 s), at most 60 s, re-encoded to H.264 (`libx264`, CRF 24, at most 1920 x 1920, at the recording's own measured frame rate) in an mp4 with the index up front (`+faststart`), with sound only when the camera's recording audio is usable (on the Backyard camera it is not: the NVR's RTSP audio there has no valid timestamps, and the Events Recorder's clips of it carry the same damage). The NVR is asked again every 30 seconds while it fails; a visit ends as `none` only five minutes after it started AND after one last NVR try has failed (or the camera has no NVR recording). The recording stream begins at the keyframe before the requested time, so the cut measures how much lead-in came with it and trims it off. Cuts run one at a time, under `nice`, one ffmpeg copy plus one encode each; the NVR's recording is H.265 on some cameras.

**Backfill.** At start-up (30 s after the plugin starts) and after the 03:30 maintenance every day, seen visits that ended with `clip.state: "none"` and started inside the NVR's retention (its "Video Retention (Days)" setting, read from Scrypted NVR; 14 days when the NVR does not delete by age; plus a 12-hour margin) get the same two-step lookup (Events Recorder, then NVR), oldest first, and become `ready` with a `visit_updated` event. A visit marked "not an animal", every heard visit, and every clip a person deleted (`clip.state: "deleted"`) are never touched. A run that leaves visits behind because a cut failed (not because the NVR no longer has the footage) is repeated after 15 minutes, up to three times in a row. What the last run did is in `GET health` under `clips.lastBackfill`.

**Kestrel keeps its own copy of every clip.** When a clip becomes `ready` it is copied into `/NVR/kestrel/clips/<camera id>/<visit id>.mp4` on the NVR's big disk (not the plugin volume), because the Events Recorder prunes its clips and the NVR deletes its footage after its retention. A clip cut from the NVR is written there directly; a file another plugin wrote is copied only once it has been untouched for 3 seconds, so a clip still being written is never kept half-finished. The copy is outside the 300 MB media budget and is never pruned by it (even a kept clip placed inside the media directory is neither counted nor deleted); only `POST clips/delete` removes one. Clips that were already `ready` before this existed are copied in the background, a few every 5 seconds (the Events Recorder's original is left where it is); a copy that fails leaves the Events Recorder's file linked and is retried every 10 minutes. Every `ready` clip's file is checked, all of them in batches (not only the latest visits): a file that vanished turns its clip into `deleted` (no `deletedBy`) and publishes `visit_updated`.

The visit's `clip` object: `{ state: "pending" | "ready" | "none" | "deleted", expectedReadyAt, url?, source?, deletedBy? }`. `source` (`"events"` or `"nvr"`, on `ready` clips; older clips read `"events"`) says where the clip came from; `deletedBy: "user"` (on `deleted` clips) says a person deleted it through `clips/delete`, as opposed to a file that went missing.

- `GET clips/storage` (optional `?olderThan=<ms epoch in the past>`) answers `{ count, bytes, oldestAt, byReason: { notAnimal: { count, bytes }, unconfirmed: { count, bytes } } }`: the clips Kestrel holds (a `ready` clip with Kestrel's own copy), their total size, the start of the oldest visit among them (`null` when there are none), and how many belong to visits marked not an animal or can't tell (`notAnimal`: status `not_animal` or `unknown`) or still carrying the model's own guess (`unconfirmed`: status `auto` or `learned`). With `olderThan` everything, `byReason` included, only counts visits that started before it. A bad `olderThan` is a 400.
- `POST clips/delete` takes exactly one of `{ "visitIds": ["<id>", ...] }` (1 to 1000), `{ "olderThan": <ms epoch in the past> }` or `{ "reason": "notAnimal" }` (visits marked not an animal or can't tell), and answers `{ deleted, freedBytes }`. It removes the clip files (only ever files inside the clip store; another plugin's file is left alone), sets each clip to `deleted` with `deletedBy: "user"` and publishes one `visit_updated` per visit; the visits, photos and everything else stay. A clip whose file cannot be removed is left as it was. Any other body is a 400.

## Local checks

Run `npm run build`, `npm run test:store`, `npm run test:seen`, `npm run test:clips`, `npm run test:heard`, `npm run test:seasonal`, `npm run test:events`, `npm run test:live` and `npm run test:learning` from this directory.

Per-camera detector checks are stored in SQLite by America/New_York calendar day; visit totals are counted from persisted visits in that same day window. Daily check rows older than 30 days are pruned.
